ChatHub
多模型接入的真实边界

它不是新的模型，也不是企业级智能网关。它是一个浏览器端多模型客户端：用统一 Adapter 同时容纳官方 API 和网页登录会话，再把不同流式协议归一给同一个上层界面。

reference-only

适合提炼 Provider Adapter、Browser Bridge、统一流式事件和并发执行方式；不建议直接 Fork 为生产底座，也不值得继续修复仓库中的旧模型和网页私有接口。

四层，而不是一个“万能调度器”

API Key 或 Cookie 只解决鉴权；每家模型仍要适配请求、流式事件、上下文、工具、文件、能力和错误。真正的调度位于这些 Adapter 之上。

01 / AUTH

API Key、OAuth、Cookie、Session、Access Token、CSRF。

→
02 / ADAPTER

把统一消息转换成 OpenAI、Claude、Gemini 或网页内部协议。

→
03 / STREAM

归一 SSE、ReadableStream、WebSocket、工具参数和错误事件。

→
04 / ROUTER

负责选择、切换、并发、取消、重试、fallback 和成本策略。

两条接入路径

ChatHub 的核心不是只使用 API Key。它同时实现官方 API Adapter 和 Browser Session Adapter；两者共享上层 Bot 接口，但稳定性、权限和适用范围不同。

PATH A / OFFICIAL API

API Key 与官方协议

通过 OpenAI、Azure、Anthropic、Gemini、OpenRouter 等 API 或 SDK，按官方文档适配。

读取平台托管 Key 或用户自带 API Key。
根据 modelId 选择对应 Provider Adapter。
转换消息、图片、文件、工具和生成参数。
解析流式事件并转换成统一事件。
PATH B / BROWSER SESSION

Cookie 与网页登录会话

用户先在浏览器登录目标网站，扩展复用 Cookie/Session，获取 Token 或在页面上下文调用内部接口。

检测用户登录状态和目标网页标签页。
获取 Access Token、CSRF 或 Conversation 信息。
必要时由 Content Script 在页面上下文代理请求。
通过 Runtime Port 把流式结果传回扩展 UI。
这条路径通常没有公开稳定的官方手册，依赖网页内部协议分析；适合本地实验，不应默认成为生产架构。

切换与并发

两种产品效果建立在同一个模型注册表和统一 Adapter 上。区别只是调用一个 Adapter，还是同时启动多个独立流。

自由切换模型

currentModel = "chatgpt"
        ↓ 用户切换
currentModel = "claude"
        ↓
createBotInstance("claude")
        ↓
后续请求由 Claude Adapter 处理
一个入口，多模型回复

同一个 prompt
  ├─ ChatGPT Adapter → Stream A
  ├─ Claude Adapter  → Stream B
  └─ Gemini Adapter  → Stream C

三个请求独立并发、独立取消、独立计费
ChatHub 按 Bot 分开保存状态，更接近切换不同模型自己的会话。若要在同一对话中无缝换模型，必须由我们的系统保存统一消息历史并逐家转换。

对我们的意义

不是继续研究 ChatHub 的旧接口，而是把它展示出的通用边界重建为可测试、可维护、与厂商解耦的内部能力。

能力研究价值采用判断
Provider Adapter 规范高统一请求、模型发现、能力声明和流式输出，是上层应用解耦的基础。
Browser Bridge中高Content Script、页面上下文代理和 Runtime Port 可迁移到本地浏览器助手。
统一流式事件高支撑切换、并发、工具调用、取消、错误和用量统计。
多模型并发中实现简单；真正价值来自路由、裁判、综合与成本控制。
现有具体 Adapter低模型名、私有 URL 和网页协议已经明显老化，只能作为历史样例。
企业生产底座低缺少服务端密钥、RBAC、审计、配额、测试、观测和合规治理。

后期应沉淀什么

建议把研究产物转化为六个独立模块。官方 API 是主路径，浏览器会话必须隔离成可选实验能力。

Provider SDK

统一 `validateAuth`、`listModels`、`streamChat`、错误码和生命周期。

Auth Strategies

托管 API Key、BYOK、官方 OAuth、Browser Session 四种认证策略。

Unified Protocol

统一 Message、Content、Tool Call、Stream Event、Usage 和附件协议。

Model Registry

记录模型能力、上下文、价格、可用性和厂商版本，不再硬编码 UI。

Model Executor

实现 single、parallel、fallback、race、route、judge 和 synthesize。

Browser Bridge

抽离页面注入、会话检测、请求代理、消息校验和权限治理。

研究收束判断

ChatHub 本身进入 reference-only：保留证据和架构结论，不继续追踪旧 Bot；未来研究转向我们的统一协议和三家官方 API 验证。

继续研究

  • OpenAI、Anthropic、Gemini 官方流式协议。
  • 同一对话跨模型继续。
  • Tool Call、文件、用量和错误标准化。
  • Browser Bridge 的最小权限实验。
  • fallback、成本路由、模型裁判与综合。

停止投入

  • 修复 GPT-3.5、Claude 2、Bard 和旧 Bing。
  • 复用硬编码网页 URL、Headers 和模型列表。
  • 把 Web Cookie 路径包装成稳定生产能力。
  • 沿用项目的正则解析式单工具 Agent。
  • 直接 Fork 上游并作为闭源产品继续开发。
