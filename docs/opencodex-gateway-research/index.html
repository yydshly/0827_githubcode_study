OpenCodex / CC Switch / AI Gateway

改变模型入口，
不替代 Agent 内核。

我们的理解是对的：通过配置让 Codex、Claude Code 等客户端把模型请求发到网关；网关再做协议适配、模型与账号调度、失败切换和响应还原。客户端仍然负责代码理解、Agent 循环和本地工具执行。

看懂完整链路 直接做技术选型
入口 Base URL / Provider 中间层 协议 + 路由 + 治理 边界 不接管本地 Agent 执行

准确说法 这是显式配置的模型网关，不是网络劫持；它控制“模型大脑供应链”，不是替代 Codex / Claude Code。

02 / RESPONSIBILITY

三方都很重要，职责不能混。

Codex 和 Claude Code 不是空壳。它们提供 Agent 执行环境；网关提供模型供应链控制；模型供应商提供实际推理。

A

CLIENT OWNS

Agent 执行内核

  • 读取代码仓库与组织上下文
  • 规划下一步并维护多轮循环
  • 调用终端、编辑器、MCP 和本地工具
  • 权限确认与执行结果回填
B

GATEWAY OWNS

模型供应链控制

  • Responses / Messages / Chat 的语义转换
  • 模型、供应商、密钥与账号路由
  • 流式事件、Tool Call 和 Thinking 还原
  • 限流、重试、成本、日志和审计
C

PROVIDER OWNS

模型推理能力

  • 理解、推理与内容生成
  • 模型上下文与推理预算
  • 原生工具调用能力与模型特性
  • 官方服务可用性和计费规则

ROUND TRIP

一个任务不是一次转发，而是多轮闭环。

每一次工具执行都会产生新结果，再由客户端组织成下一轮模型请求。网关需要在每一轮保持协议、会话和路由语义一致。

  1. 01用户提出任务
  2. 02客户端构造请求
  3. 03网关适配并路由
  4. 04模型返回决策
  5. 05客户端执行工具
  6. 06结果进入下一轮

05 / RECOMMENDED ARCHITECTURE

最有价值的是分层，不是堆代理。

建议把 Agent 特有语义和通用流量治理分开。能原生透传时就透传，只有协议不同时才转换。

CLIENTSCodex · Claude Code · OpenCode仓库理解、Agent 循环、本地工具
原生 Agent 协议
LAYER 1薄 Agent 兼容层Tool / Thinking / Stream / Context semantics
统一内部契约或原生透传
LAYER 2模型网关与治理Auth · Route · Retry · Limit · Observe
供应商原生协议
UPSTREAM官方 API / 自建推理OpenAI · Anthropic · Gemini · Local

推荐每层只有一个明确责任；请求 ID、错误和成本可贯穿全链路。

避免连续两个网关都重写 Tool Call、流式事件和模型名。

必须为原生协议保留透传和回归测试，避免“HTTP 200 但 Agent 已失真”。

07 / NON-NEGOTIABLES

真正难的不是转发，是正确、安全和可解释。

01

协议正确性

不能只验证 HTTP 200。要检查事件顺序、工具关联、终止原因、缓存、Token 和错误映射。

02

密钥与租户隔离

上游凭据只留在服务端，加密保存、最小权限、轮换；日志不能泄露请求内容或密钥。

03

上游授权与透明度

账号池用于授权范围内的可靠性，不用于绕过限额或共享个人凭据；实际模型和计费必须透明。

04

许可证与商业边界

固定版本逐项核查许可证。特别是 AGPL、附加条款和企业功能的开源/商业边界。

08 / SOURCES
