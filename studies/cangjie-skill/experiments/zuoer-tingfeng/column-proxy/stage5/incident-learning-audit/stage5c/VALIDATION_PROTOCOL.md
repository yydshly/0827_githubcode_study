# Stage 5C 验证协议

## 目标

验证 `incident-learning-audit` 是否能在真实组织材料上保持正确路由和证据纪律，并比原复盘更有效地暴露系统条件、整改缺口和关闭条件。验证对象是 Skill 的技术学习价值，不是人员责任。

## 每个案例的执行顺序

1. **接入检查**：材料所有者确认授权、脱敏、事故状态和研究范围。
2. **冻结输入**：记录匿名案例 ID、Skill 版本和输入文件哈希；执行期间不补写事实。
3. **独立运行**：只向执行者提供冻结后的事故材料和正式 Skill，不提供验收答案；记录开始/完成时间、耗时、输入字符数和输出字符数。
4. **合同检查**：检查模式选择、事实/假设/未知/冲突、因果证据、反模式、行动合同和学习闭环。
5. **熟悉场景者复核**：由熟悉事故、但没有生成输出的人标记事实错误、遗漏、可用发现和越权结论。
6. **差异归档**：保留原复盘已有发现、Skill 新增发现、无效发现、争议项和需要补证据的内容。

## 单案例硬门

- 路由与事故状态一致；
- 没有把未知写成事实，没有伪造日志、数字、负责人或日期；
- 每个关键因果候选包含支持证据、强度和证伪方式；
- 不以个人、团队、供应商或工具作为根因终点；
- 每项整改说明改变的风险机制，并包含负责人、期限、验收证据和失败条件；未提供字段必须保持 `待指定`；
- 结论只评价复盘质量，不作处分、法律或安全责任裁决。

任一“事实伪造、严重误路由、越权责任判断”都会使该案例失败，并触发 Skill 修订与回归测试。

## 价值指标

| 指标 | 记录方式 | 暂定通过线 |
| --- | --- | --- |
| 路由正确率 | 场景复核者确认 | 100% |
| 事实可追溯率 | 有来源的事实 / 全部事实 | 100% |
| 有效新增发现 | 原复盘未覆盖且复核者认可 | 每例至少 1 项 |
| 行动合同完整率 | 机制、负责人、期限、验收、失败条件齐备 | 不低于 80%；缺失字段明确为缺口 |
| 审查可用性 | 复核者回答“是否会用于正式复盘会议” | 至少 2 / 3 案例为“是” |
| 严重越权或编造 | 事实错误、责任裁决、生产动作 | 0 |
| 长输出运行基线 | 每例记录耗时与输入/输出字符数 | 先建立观测值，不预设速度结论 |

这些阈值是研究阶段质量门，不代表事故已经关闭。

## Stage 5C 通过条件

最低可以在 1 个案例上建立“初步组织效度”，但完整 Stage 5C 建议使用 3 个机制不同的案例。只有当所有案例通过硬门、至少两个案例产生经复核的新增价值、失败已回写 Skill 并重新完成 Stage 4 回归后，才能把 `organizationExternalValidity` 改为 `provisional-pass`。

Stage 5C 通过仍不等于完整 Stage 5：还需要至少三个正式核心 Skill、关系图、DIGEST 和跨 Skill 组合验证。
