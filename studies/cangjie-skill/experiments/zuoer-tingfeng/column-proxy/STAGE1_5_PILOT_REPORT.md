## 1. 结论

原候选 **“线上故障复盘”不能原样进入 Stage 2**。

它通过 V1 跨域和 V2 预测力，但“时间线、5 Whys、无责复盘、行动项”已经是通用 SRE 常识，原形态未通过严格 V3 独特性。若原样制作 Skill，只会得到另一份通用事故模板。

本试点把它收窄为 **“系统性故障学习审查”**：不负责取代 incident management，而是专门审查复盘是否停在个人归责、直接诱因、局部补丁或复杂流程，并要求跨层整改与复发验证。修订后的候选获得 **provisional pass**，等待用户确认后才能进入 Stage 2。

## 4. 外部需求校准

2026-08-28 回查的官方资料显示：

- Google SRE 把 postmortem 视为记录影响、处置、原因和防复发行动的正式学习机制，并强调无责；
- AWS Well-Architected 把 post-incident analysis 评为高风险缺失项，要求深入促成因素、共享知识和可跟踪整改；
- Microsoft Azure Well-Architected 把事故审查、演练、通信计划和生产监控反馈纳入运维成熟度。

这证明“故障复盘”有持续外部需求，同时也证明其通用部分不具有书籍独占性。书籍资产的价值必须来自更具体的判断顺序和边界。

## 5. 测试设计

冻结测试集共 18 个案例：

| 类型 | 数量 | 预期行为 |
| --- | ---: | --- |
| 核心域 | 8 | 完整运行系统学习审查 |
| 信息不足 | 3 | 只列假设、未知和取证计划，不宣布根因 |
| 活动事故 | 2 | 先止血和保存证据，等待稳定后复盘 |
| 相邻域 | 2 | 只迁移方法并显示未验证警告 |
| 域外 | 3 | 停止并转专业角色 |

结构校验结果为 PASS，18 个 ID 和问题均唯一，五种路由状态完整，所有案例都有正向和禁止行为断言。结构化结果见 [validation.json](stage1.5/incident-postmortem/validation.json)。

这不是 18/18 的模型行为通过率。测试只是在 Stage 1.5 冻结可复跑的验收合同；独立运行和混淆测试属于 Stage 4。

## 6. 与普通模板的增量

合成案例 `C02` 的协议级人工对照显示：

| 能力 | 最小四字段模板 | 修订候选 |
| --- | --- | --- |
| 根因 | 容易停在“AI 配置错误/审核不严” | 继续检查验证、发布、金丝雀、回滚和授权机制 |
| 证据 | 不强制区分事实与假设 | 明确事实、假设、未知、冲突和证伪条件 |
| 整改 | 容易变成培训、禁用或增加审批 | 要求机制、负责人、截止和可注入复发验证 |
| 组织学习 | 可选 | 强制审查归责、局部补丁和复杂度增殖 |

协议级评分为最小基线 42/100、修订候选 93/100。该分数是设计审查，不是独立模型实验。完整案例见 [工作示例](stage1.5/incident-postmortem/WORKED_EXAMPLE.md)。

## 7. 当前价值判断

该试点回答了“从书里沉淀能力如何落地”：

1. 书籍不是答案数据库，而是候选判断方式的来源；
2. 通用常识会在 V3 被淘汰，避免为已有能力重复造 Skill；
3. 被保留的部分必须改变现实任务中的判断、停止条件或验收方式；
4. 测试集先冻结，后续 Skill 才有可检验的行为合同。

对我们的直接价值，是获得了一个比通用复盘模板更窄、更可路由、也更容易测试的能力候选；同时证明 cangjie-skill 的关键价值不在“多生成 Skill”，而在“有证据地少生成 Skill”。
