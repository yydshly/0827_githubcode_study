## 任务

在生产事故已经稳定后，审查一份事故材料或复盘草稿，识别它是否停留在直接诱因、个人归责或局部补丁，并把整改推进到可验证的系统学习闭环。

它不是通用事故指挥器，也不替代安全、法律、医疗或人事调查。

## 触发条件

完整执行需要同时满足：

1. 对象是软件、服务、数据、发布、基础设施或研发协作造成的生产事件；
2. 事故已经稳定，或用户明确要求审查事后材料；
3. 至少提供影响、时间线、日志/监控/变更记录或复盘草稿中的一类证据。

## 路由与停止条件

| 输入状态 | 处理方式 |
| --- | --- |
| 技术事故已稳定且有证据 | 核心域：运行完整审查 |
| 技术事故已稳定但证据不足 | 信息缺口模式：只列事实、假设、未知项和取证计划，不宣布根因 |
| 事故仍在扩大或用户仍受影响 | 转入止血与恢复；记录材料，暂不运行完整复盘 |
| 项目延期、客服升级等非可靠性复盘 | 相邻域：只迁移学习闭环，并标记尚未验证 |
| 医疗、法律责任、证券投资或员工处分 | 停止；建议相应专业角色参与 |
| 纯架构评审、学习规划或绩效诊断 | 不触发，交给兄弟能力 |

## 最小输入

- 当前状态：是否恢复、仍有哪些用户风险；
- 影响：用户、业务、数据与持续时间；
- 时间线：发现、升级、处置、恢复节点；
- 证据：监控、日志、调用链、变更、发布、工单和沟通记录；
- 临时动作：重启、限流、回滚、降级、热修及其结果；
- 系统背景：服务边界、关键依赖、责任团队和历史同类事件；
- 已有结论或复盘草稿。

缺少的字段必须进入“未知项”，不能由模型补写。

## 执行协议

### 0. 阶段门

先判断事故是否稳定。若未稳定，只输出当前风险、恢复优先级、待保存证据和转入复盘的条件。

### 1. 证据账本

把所有陈述标成：

- **事实**：有时间戳、指标、日志、变更或多方记录支持；
- **假设**：能够解释部分现象，但尚缺验证；
- **未知**：当前材料无法判断；
- **冲突**：不同来源不一致，需要重新取证。

### 2. 用户影响时间线

按“事件—观察—决策—动作—结果”还原时间线，优先呈现用户可见影响。禁止把聊天记录顺序直接当成因果关系。

### 3. 因果阶梯

从直接触发向下审查，但允许分支，不强迫凑满五层：

1. 直接触发与故障机制；
2. 测试、监控、发布、回滚、容量和依赖条件；
3. 责任边界、协作和运行流程；
4. 目标、激励、授权和组织文化。

每一步都要回答“有什么证据”和“什么观察可以证伪”。“人为失误”“操作不规范”不能作为终点。

### 4. 四项反模式审查

- **归责替代治理**：整改是否主要是处分、培训或要求更小心；
- **局部补丁**：是否只修当前实例，没有覆盖同类风险；
- **复杂度增殖**：是否用更多审批、重复系统或人工看守掩盖原结构问题；
- **不可验收**：行动是否没有负责人、期限、成功指标或复发验证。

### 5. 整改组合

行动至少覆盖其中两类，并说明为何适用：

- 降低发生概率；
- 缩小影响面；
- 缩短发现与定位时间；
- 缩短恢复时间；
- 简化架构、流程或责任边界；
- 把教训写回运行手册、测试、发布门或演练。

每项行动包含：机制、负责人、优先级、截止时间、验收证据、失败或回滚条件。

### 6. 关闭学习环

定义复查日期和一个“复发验证”：同类事件再次发生时，哪项可观察指标应当改变。没有复查和验证的行动项不得标记完成。

## 输出契约

1. 适用域与当前阶段；
2. 事故摘要和影响；
3. 事实 / 假设 / 未知 / 冲突账本；
4. 用户影响时间线；
5. 因果阶梯与证据强度；
6. 四项反模式审查；
7. 分层整改表；
8. 未决问题、复查时间与复发验证。

## 硬边界

- 不凭缺失的日志或指标宣布单一根因；
- 不把个人、团队或 AI 工具命名为“根因”；
- 无责不等于无行动责任，行动仍需明确负责人；
- 不自动执行回滚、发布、删库、封禁账户或通知外部人员；
- 涉及安全事件、个人数据、合规或法律归责时，保留证据并要求相应专业角色参与；
- 不引用或分发代理语料长段正文。
