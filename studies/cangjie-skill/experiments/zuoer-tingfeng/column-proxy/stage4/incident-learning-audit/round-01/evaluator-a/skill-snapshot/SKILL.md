# 系统性故障学习审查

把已经稳定的生产事故或复盘草稿，从“发生了什么”推进到“系统为何允许它发生、整改如何被验证”。核心产物是证据账本、因果阶梯、反模式审查和可验收的学习闭环，不是更长的事故摘要。

## R — 原文

> “一个技术问题，后面隐藏的是工程能力问题，工程能力问题后面隐藏的是管理问题，管理问题后面隐藏的是一个公司文化的问题……”
>
> — 陈皓，《左耳听风》专栏代理语料，18｜故障处理最佳实践：故障改进

来源边界：当前研究使用公开第三方专栏代理语料，不把这段材料冒充纸质书原文或完整书稿。

## I — 方法论骨架

事故的直接触发只解释“这一次如何发生”，不能自动解释“系统为什么没有阻止、发现或限制它”。
先把事实、假设、未知和冲突分开，证据不足时暂停根因结论。
再以用户影响为主线，连接观察、决策、动作和结果，而不是把聊天顺序当作因果。
沿技术机制、工程控制、协作流程、责任边界和组织激励逐层追因，允许多条因果分支。
重点审查整改是否退化成处分、培训、更多审批、旁路系统或一次性局部补丁。
有效行动应改变发生概率、影响范围、发现速度、恢复速度或系统复杂度，并能够验收。
复盘只有在负责人、期限、复查日期和复发验证都明确后，才形成学习闭环。

## A1 — 书中的应用

### 慢 SQL 故障的连续追因

- **问题**：作者帮助一家公司复盘慢 SQL，直接诱因只是“一条 SQL 很慢”。
- **方法论的使用**：没有停在 SQL 本身，而是继续追问报警为何晚了 27 分钟、为何只发邮件、为何 15 分钟后才定位、为何缺少 Nginx 指标、为何误判 DDoS、为何上线前没有性能测试和 DBA 评审。
- **结论**：同一次事件同时暴露了监控、诊断、发布、测试和评审等多层系统条件。
- **结果**：一个局部技术问题被转化为跨层改进清单，而不是只优化当前 SQL。

## A2 — 触发场景

### 应当使用

- 生产事故已经稳定，用户要求审查事故材料、RCA 或复盘草稿。
- 已有结论把“人为失误”“AI 生成错误”“操作不规范”写成根因，需要检查是否停在表面。
- 整改主要是“加强意识、增加审批、再加监控、以后小心”，需要判断是否真正降低同类风险。
- 同类事故重复发生，需要判断此前行动为何没有改变可观察结果。
- 用户需要把事实、推测和未知项分开，并建立可验收的整改闭环。

### 常见语言信号

- “帮我审查这份故障复盘。”
- “这个根因分析是不是太表面？”
- “这些整改项真的能防止复发吗？”
- “Review this postmortem / RCA / corrective actions.”
- “Are we blaming the operator instead of fixing the system?”

### 与相邻能力的初步区分

- **活动事故响应**：用户仍受影响或事故仍在扩大时，优先止损、恢复和保全证据，不运行完整复盘。
- **架构权衡**：没有具体生产事故、只是在比较未来方案时，应使用架构决策能力。
- **代码审查**：只检查代码正确性、风格或安全性时，不触发本能力。
- **绩效或纪律处理**：本能力分析系统学习，不判断员工处分。

Stage 3 建立能力网络后，再把这些相邻能力回填为正式关系。

## E — 可执行步骤

### 0. 先做阶段门和领域路由

判断对象是否是技术生产事件、事故是否稳定、证据是否达到最小门槛，以及是否进入医疗、法律、证券、隐私或纪律调查等高风险领域。

- 完成标准：明确选择 `full_review`、`evidence_gap`、`active_handoff`、`adjacent_transfer` 或 `stop` 之一。
- 判停条件：事故仍在扩大时只输出恢复优先级、待保存证据和转入复盘的条件；高风险域停止归责判断并建议相应专业角色参与。
- 需要具体路由和最小输入时，读取 [references/evidence-and-routing.md](references/evidence-and-routing.md)。

### 1. 建立证据账本

把关键陈述分别标记为事实、假设、未知或冲突；事实应指向时间戳、指标、日志、调用链、变更、工单或多方记录。

- 完成标准：每个根因候选都能看出证据状态；缺失字段进入未知项，不补写。
- 判停条件：证据不足以支持因果分析时，切换为 `evidence_gap`，只给取证计划，不宣布根因。

### 2. 还原用户影响时间线

按“事件—观察—决策—动作—结果”排列节点，优先说明用户、业务、数据和持续时间的变化。

- 完成标准：能区分事件发生、系统发现、人员响应、影响控制和服务恢复的时间；不把时间先后直接写成因果。

### 3. 构建有证据的因果阶梯

从直接触发向技术机制、测试/监控/发布/回滚/容量/依赖、协作流程、责任边界和组织激励继续追问。允许多个原因汇合，也允许一项原因造成多个结果。

- 完成标准：每条关键因果声明同时写出支持证据、证据强度和能够证伪它的观察。
- 判停条件：“人为失误”“操作不规范”“工具出错”不能作为终点；没有进一步证据时将后续解释标成假设或未知。

### 4. 审查四类表面整改

逐项检查：归责替代治理、局部补丁、复杂度增殖、不可验收。

- 完成标准：说明每个已有行动实际改变哪一种风险机制；没有机制说明的行动标为待重写，而不是仅凭措辞判定好坏。

### 5. 形成分层整改组合

优先选择能够降低发生概率、缩小影响面、缩短发现定位时间、缩短恢复时间、简化架构流程或把教训写回测试/发布门/运行手册/演练的行动。至少覆盖两类机制，除非证据表明单一机制已足够。

- 完成标准：每项行动包含机制、负责人、优先级、截止时间、验收证据，以及失败或回滚条件。
- 措辞“加强意识”“持续关注”“以后小心”不能单独成为可接受行动。

### 6. 关闭学习环

为行动定义复查日期和复发验证：若同类事件再次出现，哪一个可观察指标、响应时长、影响范围或拦截结果应当改变。

- 完成标准：未决问题、复查时间、成功指标和复发验证完整；缺少验证的行动不得标记完成。

### 7. 按响应模式交付结果

输出必须匹配步骤 0 的路线。运行完整审查或需要评分时，读取 [references/output-contract.md](references/output-contract.md)。不要为了填满模板而编造内容；空缺应保留为未知项。

## B — 边界

### 不要这样使用

- 不在事故仍在扩大时用复盘替代止损和恢复。
- 不凭缺失的日志、指标或变更记录宣布单一根因。
- 不把个人、团队、供应商或 AI 工具直接命名为根因；应继续检查系统为何允许单点行为变成用户影响。
- 无责不等于无行动责任；整改仍需明确负责人、期限和验收证据。
- 不自动执行回滚、发布、删库、封禁账户、修改配置或通知外部人员；这些动作需要独立授权和相应操作流程。
- 涉及安全事件、个人数据、合规或法律责任时，优先保全证据并要求安全、隐私或法律角色参与。
- 不把相邻域的迁移建议声称为已验证结论。
- 技术产品、标准或平台能力可能随时间变化时，在给出具体实施建议前重新核验官方资料。

### 失败模式

- **用惩罚替代治理**：可能制造保守、隐瞒和责任切割，却没有改变故障机制。
- **用流程堆叠替代修复**：增加审批、人工看守或旁路系统可能继续放大复杂度。
- **机械凑够五个为什么**：追问数量不是目标；没有证据的深层原因只是故事。
- **把文档完成当作风险下降**：如果没有复查和复发验证，行动项关闭不代表系统已经学习。
